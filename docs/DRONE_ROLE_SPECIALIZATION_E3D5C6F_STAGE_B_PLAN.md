# E3d5c6f — Stage B Physical Two-Drone Vertical Slice: Scoped Implementation Plan

**Prepared:** 2026-11-24. **Status:** Stage B planning begun; gameplay implementation NOT started. Requires separate explicit code-scope approval. Branch: `feature/e3d5c6f-stage-a-role-contracts`; draft PR #1 remains unmerged. Developer confirmed both Stage A isolated F6 fixtures passed locally (two scenes with 6 and 7 labeled sections); no fresh combined regression yet. Historical E3d5c6e baseline: **63 unique suites / 880 manifest-expected checks**, previously developer-accepted.

## Desired end-to-end vertical slice

One real, explicitly authorized Ammunition Press job; original priority/FIFO queue; one real Starter Storage with 15 Test Ingots; one original site-owned receiver/buffer; one original escrow; one Hub; one **logistics** drone and one **construction** drone with distinct runtime identities; one worker slot. Logistics drone physically collects exactly five ingots at the original Storage, flies to the original Press site, unloads exactly five into the pinned receiver, and hands off a verified receipt. Logistics then safely returns/rearms, WITHOUT worker readiness. Construction drone must be independently assigned through that receipt, fly to the original site on metered energy, and only then obtain the finite worker slot through physical presence plus existing power and original held escrow. Exactly one authoritative job clock completes the existing **18-second** Press. Completed building consumes original escrow once; source Storage remains at **10 ingots**. The slice cannot fabricate or virtually teleport material.

**No permanent fleet scheduling, multi-site overlap, multi-trip bills, save/load, research progression, ore/power expansion, cancellation-return transport, Hub charge-fairness, blackout parking for the two-role case, or zombie combat.** These are separate Stage C/D or later gates. Stage B must fail closed, preserve real cargo/location/escrow, and never claim full recovery behavior when cancellation occurs during transport.

## Architecture decisions grounded in current code

1. **No widening of the accepted `PrototypeDroneAutomaticDispatch`.** Its `_scope_reason()` requires exactly one `PrototypeConstructionWorkerDrone` and a one-slot scheduler. Never put a second drone under that dispatcher, run two dispatchers, or reuse an active E3d5c6e adapter `_process` in the new scene.
2. **Use only one new orchestration owner** in the exact E3d5c6f scene, responsible for bounded ticks of both physical entities, one readiness reconcile and one job advance per frame. Keep site `set_process(false)` while explicitly driven, and count/assert the single owner in isolated tests.
3. **Preserve existing original job/queue, source/staging, supplier claims, escrow, power coordinator and scheduler as authorities.** Any role-phase ledger is subordinate; its receipt is proof, not inventory, job or timer authority.
4. **Logistics path:** add an E3d5c6f-only transport role adapter/state machine, if existing drone APIs can be safely reused under exact identity/role guards. Require authentic supplier reservation, pickup progression, cargo custody, finite source/site movement and complete unloading. Existing `release_docked_cargo_assignment` requires terminal construction, cleared escrow and no scheduler tracking; do **not** call it at nonterminal handoff. Add a new isolated guarded nonterminal *transport-only* release path after cargo is provably empty and safe physical return to Hub.
5. **Builder path:** existing `_delivered_worker_valid` / `_promote_delivered_worker`, `BlueprintConstructionSlotScheduler.bind_delivered_site_drone` and `BlueprintConstructionReadinessCoordinator.admit_delivered_worker` require the original delivering drone. Do **not** bypass them with a fake DELIVERED flag. Add a separate E3d5c6f-only proof-backed builder binding path: exact receipt, distinct builder identity, empty builder cargo, original job/site, actual arrival and power/material checks, then existing single-slot scheduler admission.
6. **Stage A contracts require a scoped lifecycle extension before Stage B:** `receipt_valid` currently requires `QUEUED` (appropriate before worker admission), and `claim_logistics` denies all further leases while `_leases` is nonempty. Introduce exact-scoped phase transitions/tombstone handling to prevent stale/replayed receipts, early builder launch and later ticket deadlock; keep Stage A public behavior and tests passing. Never expose externally mutable receipt state.
7. **Energy and return:** both drones retain unique physical identity and finite battery. For Stage B's single-mission case, demonstrate actual route preflight, no free charging and nonterminal transport return. Shared-Hub fairness and blackout handling across two roles are not assumed solved until Stage C.
8. **Cancellation/loss during this slice:** stop new launches/admissions, preserve any real item custody or original escrow; do not silently refund or transport canceled-site items. Add fail-closed negative F6 tests. Stage C will own complete physical recovery/cancellation.
9. **Exact opt-in only:** `res://scenes/core/playable_specialized_drones_e3d5c6f.tscn`; no modification to `scenes/core/main.tscn`, old accepted E3d5c6b/c/d/e scenes or old tests. New services must default OFF outside this path. Existing accepted gameplay code may need *additive guarded methods* but never alter default behavior. Maintain Godot 4.6.2 compatibility.
